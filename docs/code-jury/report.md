# ملخص

**IntelliLect** منصة تعليمية للتعلّم المتزامن تجمع بين البث المباشر منخفض الكمون وقدرات
الذكاء الاصطناعي التوليدي، بهدف تحويل الدرس عبر الإنترنت من نقل سلبي للصوت والصورة إلى
بيئة تفاعلية غنية بالبيانات.

نُفِّذ النظام بمعمارية خدمات مصغَّرة (Microservices) تضم ست خدمات خلفية وواجهة أمامية
أحادية الصفحة، تعتمد كل خدمة قاعدة بيانات خاصة بها. يقوم النظام أثناء المحاضرة بتحويل كلام
المعلّم إلى نص لحظيًا، ومقارنته بالمواد المرجعية المرفوعة للفصل عبر تقنية التوليد المعزَّز
بالاسترجاع (RAG)، ثم تزويد المعلّم بإشعارات خاصة لا يراها الطلاب، واقتراح اختبارات قصيرة،
وتوليد ملخّص للجلسة بعد انتهائها. كما يتيح النظام سبورة بيضاء تفاعلية تُسجَّل ضمن فيديو
المحاضرة نفسه.

بلغ عدد الاختبارات الآلية المكتوبة **1195** اختبارًا موزّعة على الخدمات الخلفية والواجهة
الأمامية.

# أهداف المشروع

1. **تقليل العبء الإدراكي على المعلّم**: تولّي النظام مهام المتابعة والتقييم اللحظي، ليتفرّغ
   المعلّم لجودة الشرح والتفاعل الإنساني.
2. **ترسيخ إجابات الذكاء الاصطناعي في مواد الفصل**: استخدام RAG لضمان أن تُبنى الإجابات على
   المستندات التي رفعها المعلّم لا على معرفة النموذج العامة، بما يقلّل الهلوسة (Hallucination).
3. **قياس الفهم لحظيًا**: توليد اختبارات قصيرة من الأفكار المطروحة فعليًا في المحاضرة.
4. **حفظ المحاضرة كاملة**: تسجيل الجلسة مع ما رُسم على السبورة البيضاء ضمن ملف الفيديو نفسه،
   وتوليد ملخّص نصي لها.
5. **بنية قابلة للتوسّع والصيانة**: فصل المسؤوليات بين خدمات مستقلة النشر، بحيث لا يؤدي تعطّل
   خدمة إلى تعطّل النظام بأكمله.

# تصميم النظام

## المخطط الصندوقي للنظام

![المخطط الصندوقي العام للنظام](../report/figures/arch-01-system-block.png){width=15.5cm}

يوضّح المخطط الفصل المتعمَّد بين ناقلَين للاتصال:

- **HTTP داخلي مع سرّ مشترك** (`X-Internal-Secret`) للطلب والاستجابة بين الخدمات، على مسارات
  `/api/internal` المحجوبة عن البوابة العامة.
- **RabbitMQ/MassTransit** لأحداث المجال ذات الاتجاه الواحد.

ولا يوجد نمط طلب/استجابة فوق ناقل الرسائل إطلاقًا، لأنّ حجب خدمة بانتظار ردّ عبر طابور يُنتج
تشابكًا موزّعًا (Distributed Deadlock).

## مخطط قواعد البيانات (ERD)

تملك كل خدمة قاعدة بياناتها الخاصة، لذا يُعرض المخطط منفصلًا لكل خدمة. المعرّفات العابرة
للخدمات (مثل `teacher_id`) هي معرّفات عادية وليست مفاتيح أجنبية.

# التنفيذ والاختبارات

## معمارية النظام المتبعة

### على مستوى النظام: خدمات مصغَّرة

| الخدمة | التقنية | المسؤولية |
| --- | --- | --- |
| UserManagementService | .NET 10 | الهوية، JWT ورموز التحديث، المصادقة الثنائية، الأدوار، سير الموافقة |
| ClassroomService | .NET 10 | الفصول والجلسات والملفات والاختبارات والعلامات والملخّصات |
| StreamingService | .NET 10 | غرف LiveKit ورموزها، مركز SignalR، تسجيل المحاضرة، سياسة الوسائط |
| KnowledgeService | Python / FastAPI | الاستيعاب والتقطيع والتضمين والاسترجاع |
| LiveAssistantService | Python / FastAPI | تحويل الكلام إلى نص، كشف حدود الأفكار، التحليل، توليد الاختبارات |
| EmailService | .NET 10 | مستهلك أحداث فقط، بلا واجهة HTTP |
| front-end-web | React 19 + Vite | الواجهة الأمامية: غرفة البث، السبورة، الاختبارات، لوحات المتابعة |

### داخل كل خدمة .NET: المعمارية النظيفة

تُقسَّم كل خدمة إلى `Domain` و`Application` و`Infrastructure` و`Api`، مع قاعدة تبعية واحدة:
تتّجه التبعيات نحو الداخل فقط. أثر ذلك عمليًّا أنّ منطق العمل لا يعرف شيئًا عن Entity
Framework أو عن ASP.NET، ما يجعله قابلًا للاختبار دون قاعدة بيانات.

### داخل خدمات Python: معمارية المنافذ والمحوِّلات

تُعرَّف الواجهات (Ports) في طبقة التطبيق، وتُحقَّق في طبقة البنية التحتية. مثال ذلك واجهة
`EmbeddingProvider` التي يحقّقها مزوِّد Gemini، ما يسمح باستبدال المزوِّد دون تعديل خط
الأنابيب نفسه.

## تفصيل أجزاء النظام وطريقة تنفيذ التكامل

### 1. تكامل البث المباشر

تنشئ `StreamingService` غرفة LiveKit وتُصدر رمز وصول لكل مشارك، ويحمل الرمز **الدور ضمن
بيانات التعريف (metadata)** لا ضمن الاسم، لأنّ الاسم قابل للتغيير من العميل. تتدفّق الوسائط
بين المتصفح وخادم LiveKit مباشرةً ولا تمرّ ببوابة nginx إطلاقًا.

### 2. تكامل التسجيل والسبورة البيضاء

تلتقط خدمة Egress في LiveKit **صفحة ويب كاملة** لا مسارات وسائط منفردة. لذلك أُنشئت صفحة
`/recorder` مخصّصة، يفتحها متصفّح Chrome بلا واجهة، وينتظر إشارة `START_RECORDING` قبل بدء
التسجيل. وهذا هو السبب الذي يجعل رسوم السبورة البيضاء تظهر في ملف MP4 أصلًا: فهي تُرسم ضمن
الصفحة الملتقطة.

تُخزَّن نقاط السبورة بإحداثيات **معيارية** ضمن المجال `[0,1]` منسوبةً إلى مستطيل محتوى
الفيديو، لا بالبكسل، لأنّ الإحداثيات البكسلية تضع الرسم في موضع خاطئ عند اختلاف قياس الشاشة
أو نسبة العرض إلى الارتفاع.

### 3. تكامل قاعدة المعرفة

عند رفع ملف، تُرسل `ClassroomService` طلبًا داخليًّا إلى `KnowledgeService`، التي تستوعب
الملف لا تزامنيًّا: استخراج النص، ثم تعرّف ضوئي انتقائي للصفحات الصورية فقط، ثم التقطيع،
ثم التضمين، ثم التخزين في pgvector. وتُحتسب بصمة للمحتوى (content hash) لتفادي إعادة فهرسة
الملف نفسه.

### 4. تكامل الأحداث

تُنشر أحداث المجال عبر MassTransit. وفي `KnowledgeService` استُخدم **نمط صندوق الصادر**: تُكتب
الرسالة وتغييرات البيانات ضمن معاملة واحدة، ثم يتولّى عامل منفصل نشرها. وبذلك لا تضيع الأحداث
إذا تعطّل وسيط الرسائل بين الكتابة والنشر.

## بسودوكود

### كشف حدود الفكرة التعليمية ومقارنتها بالمادة المرجعية

```text
عند وصول مقطع صوتي جديد:
    نص ← تحويل_الكلام_إلى_نص(المقطع)
    ألحق نص بنص الجلسة مع طوابعه الزمنية

    إذا كانت الفكرة قد اكتملت (سكوت كافٍ أو طول كافٍ):
        مقاطع ← بحث_دلالي(تضمين(نص), معرف_الفصل, أعلى_k)
        إذا كانت مقاطع فارغة:
            توقف            // لا مادة مرجعية تقابل هذه الفكرة
        تقييم ← قارن(شرح_المعلم = نص, المرجع = مقاطع)
        إذا كان تقييم.يوجد_نقص أو تقييم.يوجد_تعارض:
            أرسل_إشعارًا_خاصًّا(المعلم, تقييم.الملاحظة)
        سؤال ← ولّد_سؤالًا(نص, مقاطع)
        اقترح_على_المعلم(سؤال)
```

### الاسترجاع المعزَّز (RAG) للإجابة عن سؤال طالب

```text
الدخل: سؤال، معرف_الفصل
    تضمين_السؤال ← ضمّن(تعليمة_الاسترجاع + سؤال)
    مقاطع ← أقرب_الجيران(تضمين_السؤال, تصفية = معرف_الفصل, المقياس = جيب_التمام)
    إذا كانت مقاطع فارغة:
        أعد "لا تتوفر إجابة ضمن مواد هذا الفصل"
    سياق ← ادمج(مقاطع)
    إجابة ← ولّد(سياق + سؤال)
    أعد إجابة مع مصادرها
```

### حماية الإجابة الصحيحة من التسريب

```text
عند طلب الطالب لأسئلة اختبار:
    // لا يُستخدم كائن نقل البيانات الخاص بالمعلم إطلاقًا
    لكل سؤال في الاختبار:
        أعد QuizOptionStudentDto(المعرف, الترتيب, النص)
        // البنية نفسها لا تحوي حقل IsCorrect، فالتسريب مستحيل بنيويًّا
```

### أمثلة على ما تغطّيه الاختبارات

- **المنطق الهندسي للسبورة**: تحويل الإحداثيات المعيارية إلى مستطيل المحتوى بعد
  الاحتواء (letterboxing)، وهو أدقّ جزء في الميزة وأكثرها عرضة للخطأ الصامت.
- **بروتوكول السبورة**: ترميز الرسائل وفكّها، ورفض أي رسالة غير صالحة، وتقسيم الرسائل
  التي تتجاوز الحدّ الأقصى لحزمة القناة الموثوقة.
- **عزل الإجابة الصحيحة**: التحقق من أنّ ما يُرسل إلى الطالب لا يمكن أن يحمل حقل الإجابة
  الصحيحة.
- **اتساق أبعاد التضمين**: رفض التشغيل مبكرًا إذا خالف عرض المتّجه إعداد `EMBEDDING_DIM`،
  بدل أن يظهر الخطأ لاحقًا عند الإدراج في قاعدة البيانات.

### الفجوات المعروفة والخطة المقترحة

يقتصر ما هو منفَّذ حاليًّا على اختبارات الوحدة والمكوّنات. وفيما يلي الفجوات صراحةً:

| النوع | الحالة | الخطة |
| --- | --- | --- |
| **اختبارات التكامل** | مشروع مُهيَّأ لكنّه فارغ تمامًا | تشغيل الخدمة مقابل قاعدة بيانات حقيقية عبر Testcontainers، وتغطية مسار التسجيل والموافقة وتسجيل الدخول من طرف إلى طرف |
| **اختبارات الأمان** | غير منفَّذة | التحقق من رفض المسارات الداخلية بلا سرّ مشترك، ومن رفض الوصول عبر الأدوار، ومن انتهاء صلاحية الرموز |
| **اختبارات الحمل** | غير منفَّذة | قياس سعة الجلسة الحية بعدد مشاركين متزايد، ورصد إسقاط الإطارات في التسجيل |
